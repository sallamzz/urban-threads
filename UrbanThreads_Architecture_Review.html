🏗️ System Architecture Overview

The app is a Next.js 15 (App Router) application deployed on Vercel/Cloudflare. All Gameball API calls are server-proxied through Next.js Route Handlers to protect the SecretKey. The client only sees the public APIKey (for the widget). Discovery: ALL endpoints (read and write) require both APIKey + SecretKey — the tier endpoint returned 401 with APIKey-only.

✅ Code Quality & Best Practice Evaluation

Evaluated against industry standards for Next.js apps and the Gameball API documentation. Updated after development to reflect real-world discoveries.

Security — SecretKey Protection EXCELLENT

SecretKey is server-only (env var without NEXT_PUBLIC_ prefix). All Gameball API calls go through Route Handlers. Only the public APIKey is exposed for the JS widget init. Matches Gameball's security model.

Architecture — Server Proxy Pattern EXCELLENT

Every Gameball API call is proxied through dedicated Route Handlers. Clean separation of concerns. Each route has one job. The shared gameball.ts lib avoids code duplication.

API Auth — Both Keys for ALL Endpoints DISCOVERED

Corrected from original review: ALL Gameball endpoints (read AND write) require both APIKey + SecretKey. The tier-progress endpoint returned 401 with APIKey-only. The code now sends both headers in every function (gbGet, gbPost, gbDel). This is intentional, not unnecessary overhead.

Redemption Flow — Hold → Order EXCELLENT

Implements the correct 2-step redemption: POST /hold to get holdReference, then pass it in the order's redemption.pointsHoldReference field. Handles the case where no redemption is needed (skips hold).

Order Payload — totalPaid vs totalPrice EXCELLENT

Correctly sends the post-discount amount as totalPaid (what Gameball uses for reward calculation). Converts cents to dollars before sending. Includes lineItems with productId, quantity, price, title, category.

Three Event Types Covered GOOD

profile_completed (registration), write_review (product page, with has_image metadata), and purchase_completed (fire-and-forget after order, triggers Event Based Earn campaigns). All three correctly proxied through the events route.

Widget Integration — Queue Stub GOOD

Uses the official queue stub pattern: defines GbSdk.q, calls GbSdk.init() (queued), then loads the script. Only loads once (checks for #gb-sdk). Passes playerUniqueId and lang.

Registration — Idempotent + Event Sequencing GOOD

profile_completed event fires only AFTER successful registration (so the customer exists in Gameball first). Registration is idempotent. User can browse immediately even if API fails.

TypeScript — Full Type Safety GOOD

All interfaces defined in types.ts. Props are typed. API payloads use Record<string, unknown>. Minimal use of 'any' (only for Gameball SDK global).

UX — Edge Cases Handled GOOD

Empty cart states, loading skeletons, 0-points messaging, form validation, error displays, toast notifications. Post-checkout refreshes player info. Graceful fallback on API failures.

Edge Runtime GOOD

All API routes export runtime = 'edge' for fast cold starts on Cloudflare/Vercel Edge. Lightweight fetch-based implementation. Removed incompatible cache: 'no-store' for Cloudflare Workers.

Tier Progress — Raw Spend, Not Percentage FIXED

Gameball returns raw accumulated spend in dollars in the progress field (e.g. 34.99), NOT a 0-100 percentage. UserContext now divides by next.minProgress to compute the actual percentage. Also handles the minPorgress API typo.

BadgeGrid — Rewritten to Milestone-Based REWRITTEN

The /campaigns REST endpoint only surfaces Achievement/Challenge campaigns — Event Based Earn campaigns (the most common type) don't appear. BadgeGrid was completely rewritten to compute 6 milestones locally from order history and loyalty data. No external badge API needed.

Hold Route — Field Name Mapping DISCOVERED

Gameball's hold endpoint expects playerUniqueId + amount, not the customerId + pointsToHold field names used elsewhere. The hold route now maps field names correctly before forwarding.

No Hold Release on Abandon MINOR

If a user starts checkout with a hold but navigates away, the hold isn't proactively released (it expires after 10 min). In production, a beforeunload handler or timeout should call DELETE /hold.

Order API Failure is Non-Critical NOTE

The checkout page logs order API failures but continues to show success. In production, this should block the flow or retry — otherwise the user sees "order confirmed" but Gameball never tracked it.

No Pending vs Available Points MINOR

The UI shows only total points balance. Gameball has a 14-day return window where points sit in "pending" state. Production should distinguish pending vs available to prevent over-redemption.

localStorage for Orders DEMO-ONLY

Order history is stored in localStorage — acceptable for a demo. In production, orders would live in a database. The INTEGRATION_NOTES.md correctly acknowledges this as a trade-off.

No Rate Limiting on API Routes MINOR

The proxy routes don't rate-limit or validate beyond basic field checks. In production, add request throttling and more robust input validation/sanitization.

Milestone Badge System — Clean Fallback NICE

The rewritten BadgeGrid uses a pure function buildMilestones() that derives achievement status from real data. No network calls needed. Shows practical problem-solving when an API doesn't fit the use case.

Points Balance 404 Fallback NICE

Gameball returns 404 with empty body for new customers instead of { balance: 0 }. UserContext handles this gracefully by falling back to tier progress value. Multiple fallback keys checked. Shows practical API debugging experience.

Fire-and-Forget Event Pattern NICE

purchase_completed is sent via fire-and-forget (.catch(() => {})) — it's non-critical and shouldn't block the checkout flow. If the event fails, the order still succeeds. Smart tradeoff for demo reliability.

Design System Consistency NICE

Consistent navy/gold palette, custom animations (7 keyframes), reusable Button with variants, card utility class, Playfair Display for headings. Professional look for a demo.

API Discoveries

Auth Model

ALL endpoints require APIKey + SecretKey. APIKey alone only works for the JS widget init. Discovered when tier-progress returned 401.

Tier Progress Format

progress = raw accumulated spend in dollars. Must compute percentage manually: (progress / next.minProgress) * 100. API has a minPorgress typo.

Campaigns Limitation

REST /campaigns only surfaces Achievement/Challenge types. Event Based Earn campaigns are widget-only. Also returned 404 for test customers.

Points 404 Quirk

Gameball returns HTTP 404 with empty body for new customers with no points, instead of returning { balance: 0 }. Must handle gracefully.

Hold Field Names

Gameball's hold endpoint expects playerUniqueId + amount, different from the customerId + pointsToHold naming used in other endpoints.

Orders vs Events API

Orders API handles transactional earn (cashback). But Event Based Earn campaigns (1000 pts + badge) only trigger via the Events API with purchase_completed.
